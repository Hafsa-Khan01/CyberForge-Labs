# 8. SOC Tiers, Alert Lifecycle and Triage Notes

## SOC analyst tiers
SOC structures vary by organization, but the following is a common division of responsibilities.

| Tier | Typical responsibilities | Example work |
|---|---|---|
| L1 – Alert Monitoring / Triage | Monitor alert queues, validate basic evidence, enrich events, assign initial verdict and escalate | Review repeated failed logons and document source and target |
| L2 – Incident Investigation | Correlate multiple data sources, scope affected systems and coordinate containment | Investigate a suspected compromised account across endpoint and identity logs |
| L3 – Detection / Threat Hunting / Advanced Response | Handle complex incidents, threat hunting, detection engineering and advanced analysis | Develop a detection for a technique and hunt across multiple hosts |

Titles and responsibilities differ between organizations. L1 analysts should follow escalation criteria and must not perform disruptive containment actions unless authorized.

## Alert lifecycle
1. **Event generation:** A source creates a log or security event.
2. **Collection:** An agent, forwarder, syslog service or integration sends the event to the platform.
3. **Detection:** A rule, search or analytic identifies a pattern.
4. **Alert creation:** The platform creates an alert with metadata and severity.
5. **Triage:** An analyst validates the alert, checks context and gathers evidence.
6. **Classification:** The analyst records a verdict such as true positive, false positive or inconclusive.
7. **Escalation / response:** Confirmed or high-risk activity is escalated and approved response actions are coordinated.
8. **Resolution and closure:** The case is resolved, documented and closed with a clear rationale.
9. **Review and improvement:** Detection logic, procedures and lessons learned are reviewed.

Do not close an alert as a false positive merely because the behavior cannot immediately be reproduced. Use an inconclusive or needs-investigation status when evidence is insufficient, if the workflow supports it.

## Five questions every triage note must answer

| Question | What to record | Example |
|---|---|---|
| Who? | User, account, process or source identity | Account lab-user; source 192.0.2.25 |
| What? | Observed behavior and detection | Seven failed SSH authentication attempts |
| When? | Timestamp, time zone and relevant window | 2026-11-09 14:05–14:10 PKT |
| Where? | Source and destination systems, hosts and log source | Kali test VM to Ubuntu lab VM |
| Why? | Why activity is suspicious or expected, based on evidence | Repeated failures exceed the configured lab threshold |

Use documentation-safe example addresses such as those in RFC 5737 for illustrative examples. Replace them with actual lab evidence only when documenting a real test.

## Example triage note (illustrative only)
**Alert:** Repeated SSH authentication failures  
**Who:** Test account lab-user; source 192.0.2.25 (documentation example address).  
**What:** Seven failed SSH authentication attempts were recorded.  
**When:** Within a five-minute lab test window.  
**Where:** Source test VM to the Ubuntu lab host.  
**Why:** The failure count exceeded the lab threshold and is consistent with password-guessing behavior.  
**Evidence:** Authentication log entries and SIEM search results show repeated failures from the same source.  
**Verdict:** True positive for the configured detection condition, assuming the activity was generated by the controlled test. This does not mean a real compromise occurred.  
**Next step:** Record the test result, verify that no successful authentication followed, and close the lab test case. In a real environment, preserve evidence and escalate according to policy.

## Good triage practices
- Record facts separately from assumptions.
- Preserve original timestamps and identify the time zone.
- Include the exact search, rule ID or event IDs used.
- Verify source and destination direction.
- State what evidence is missing.
- Do not claim containment or remediation unless it occurred.
- Escalate when scope, impact or confidence exceeds L1 authority.
